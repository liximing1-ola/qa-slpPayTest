# qa-slpPayTest

SLP / XSG 打赏与支付链路的接口自动化用例。

- **框架**：Python 3.9+、unittest（`discover` 自动收集，不用维护用例清单）
- **依赖**：`requests` / `urllib3` / `PyMySQL` / `redis`，见 `requirements.txt`
- **覆盖**：私聊打赏、房间打赏、跨公会与跨档分成、点唱房（点歌/冠歌）、礼物优惠券、房间守护、人气加速卡、甄选礼盒、账户与房间数据校验
- **部署到云服务器**：见 [DEPLOY.md](DEPLOY.md)

当前基线（SLP 全量 137 条）：**执行 125 / 跳过 12**。跳过的是「依赖前序造数」和「功能已下线」的用例，不是缺陷；通过/失败数请以每轮报告为准（`log/notPassCase.log`、`log/failCase.log`）。

这 12 条是**刻意保留**的，不是懒得清：守护关系、星舰群这些是功能下线而非废弃，后续有恢复可能，恢复后去掉 `@unittest.skip` 就能复用（造数与断言都还在）。代价是「跳过 12」会长期出现在每轮报告里——因此判定标准是：**只要还可能恢复就留，确认永久下线的才删**。删不是禁忌，但需要一句明确的「永久下线」结论，否则等于把一段能复用的验证逻辑凭印象丢掉。

**XSG 用例集当前暂停维护**：`caseXsg/` 下 29 条保留不动，仅作为参考，不作为验收基线；slp 与 xsg 仍指向同一套测试环境（只差 `package` 参数），需要恢复时 `run_all_case.py xsg` 可直接跑。因此日常回归、基线对比只看 SLP 那 137 条。

礼物优惠券另有一个容易踩的坑：**有损 / 无损不是独立开关，而是券商品的 `coupon_type` 决定的**——`gift_discount`（89297）折扣额平台减免、收礼方按实付分成（有损）；`pro_gift_discount`（89370）平台补贴、收礼方按原价分成（无损）。`pro_gift_discount` 目前只接入房间链路，私聊会被拒单，详见 `caseSlp/test_coupon_2.py` 文件头。

## 运行方式

### 本机只做静态检查（默认）

本机不在测试环境内网，跑真实用例只会得到一屏「连不上库」的假失败——那既不是回归信号，也会把「真的全挂了」这个信号提前用掉。两个入口开跑前都会先探 MySQL / Redis / 支付接口，任一项不通就不执行任何用例、退出码 `3`，并把原因写进 `log/runCode.log`。

所以本机的固定动作是这三条，全都不连服务端、不连库：

```bash
python -m compileall -q caseSlp caseXsg caseStress common   # 语法能否解析
python -m common.selfcheck                       # 框架守卫逻辑（频控退避 / 失败现场 / 轮询读值 / 并发工具）
python pre_push_audit.py                         # 全仓审查（十四类）
```

真实执行在服务器上：`git pull --ff-only` 之后跑 `run_all_case.py` 或 `run_crontab_case.py`。只想看体检结果：`python -m common.preflight slp`（不可用时退出码同为 `3`）。

### 全量

```bash
python3 run_all_case.py slp
python3 run_all_case.py xsg
```

`run_all_case.py` 会先刷一次 token、检查代码分支，再执行全量；不带参数默认跑 SLP。传了 slp/xsg 以外的值会直接报错退出（退出码 `2`），不会静默跑全量。

### 只跑指定用例（调试主力）

用环境变量 `CASE`，逗号分隔，可以混着写：

```bash
# 整个文件（带不带 test_ 前缀、.py 后缀都行）
CASE=test_check python3 run_all_case.py slp

# 单个用例 / 整个类
CASE=test_naming_song.TestPayCreate.test_003 python3 run_all_case.py slp
CASE=test_naming_song.TestPayCreate python3 run_all_case.py slp

# 多条混搭
CASE=test_check.TestPayCreate.test_002,test_coupon python3 run_all_case.py slp
```

不设 `CASE` 就是全量。写用例名（含 `.`）时按名字加载，**名字写错（模块/类/方法不存在、前缀重复）当场报原因并以退出码 `2` 结束**：

```
[CASE] 用例名加载不到：ModuleNotFoundError: No module named 'caseStress.caseStress'
[CASE] 写法：caseStress.caseStress.test_pay_concurrent…　本轮用例目录：caseStress
```

不能把它变成报告里的一条「异常」用例——那跟用例真挂了长得一模一样，写错名字的人会去翻用例代码。也不会静默跳过。全量 `discover` 时模块导入失败仍按真失败报：那是代码坏了，不是名字写错。

名字带不带用例目录前缀都认：`caseSlp.test_check.TestPayCreate.test_002` 和 `test_check.TestPayCreate.test_002` 等价。`run_reproduce.py --case` 用的是全名，同一个用例名在两个入口不该有两套写法。前缀与实际跑的目录不一致（比如跑 `caseStress` 却写了 `caseSlp.`）会直接退出（退出码 `2`），而不是拼成 `caseStress.caseStress.…` 再报一条 `No module named` 的假失败。

### 并发与幂等（每天一次，独立执行）

```bash
python3 run_stress_case.py slp
CASE=test_pay_concurrent python3 run_stress_case.py slp    # 只跑 test_pay_concurrent 那 6 条
CASE=caseStress.test_pay_concurrent.TestConcurrentPay.test_005 python3 run_stress_case.py slp
python3 run_reproduce.py                                   # test_004 连跑 10 轮，出复现率
```

`CASE` 的两种写法等价：带 `caseStress.` 前缀的全名可以照抄 `run_reproduce.py --case` 的那个名字直接粘过来，不用管「这里要不要删前缀」。

`run_reproduce.py` 把「红 / 绿 / 未测到」分开数：**复现率 = 红 / (红 + 绿)**，
未测到（被限流挡下、根本没走到校验）与无效轮次都不进分母。每轮起独立进程，与人工
反复执行完全一致；红的那轮完整输出会落到 `log/reproduce-*.log`，可直接拿去提单。

```bash
python3 run_reproduce.py --rounds 20 --stagger 0.2
python3 run_reproduce.py --case caseStress.test_pay_concurrent.TestConcurrentPay.test_002
```

这部分用例回答的是「服务端会不会超扣、会不会重复扣费」。它们**不进全量回归**，而是单独一条 cron、每天 11:00 跑一轮，与 10:00 的全量错开一小时：用例会改账号数据，混进日常回归就没法把一次「红」归因到某一类。

两条定时任务分开还有一个实际好处：日志各归各的。`log/cron_*.log` 红 = 业务回归出问题，
`log/cron_stress_*.log` 红 = 并发缺陷，不用翻文件判断。

但它们和日常用例**当前没看到冲突，只是证据还不够硬**——双方各自在前置里清理自己依赖的数据：
余额 `prepare_test_data`、上周厅统计 `reset_room_acs`、VIP 经验值与个人人气 `prepare_vip_pop_data`、
背包 `reset_payer`。实测（2026-10-29）：先跑完 6 条并发，紧接着跑「最容易被污染」的 5 个场景族
41 条，39 条执行 0 未通过（2 条既定 skip）；可这 41 条不含 `test_gs_pay_self`，而它用的账号
`gs_A_uid`、厅 `170000211`、公会长恰好都是并发改过的对象——紧接着那一轮「并发 -> 全量」里
它确实红了 3 条（HTTP 500），单跑该模块 7 条全过，再下一轮全量又只剩 1 次 500 且换了文件。

所以「谁先谁后都行」**还没有结论**，详见下面「打赏接口 HTTP 500 偶发」。这也正是把它们拆成
两条 cron、错开一小时的理由：不靠执行顺序来保证绿，也就不需要为顺序留任何兜底。

为什么必须是独立目录 + 独立进程：

1. 节流是 App 级全局锁（`common/Request` 的 `_interval_lock` 按 `tokenName` 排队），同进程多线程会被塞进同一个窗口，每个请求至少隔 `REQUEST_INTERVAL`——那样写出来的「并发」其实是串行，测的是限流而不是服务端。所以入口在 import 任何 `common` 模块之前把间隔归零。
2. 用例会改动账号数据，混进日常回归就没法把一次「红」归因到某一类。

| 用例 | 断言 |
|---|---|
| 四账号并发打同一主播 | 扣款总额 = 成功笔数 × 单价，且余额不得为负 |
| 同账号并发两笔（余额只够一笔） | 钱与成功响应严格对应，不得透支 |
| 四账号各连发两笔相同请求 | 每个账号扣款 = 自己成功笔数 × 单价，不得透支；分成流水也按成功笔数放大；两笔全被频控挡下时判未测到 |
| 同账号并发两笔自刷（余额只够一笔） | 同上口径；分成按（账号, op）分桶、只看自己那个账号的行，按成功笔数放大；历史红过一次但 45 轮未复现，留作回归钉 |
| 四账号并发打同一主播（收款侧） | 分成流水按成功笔数放大：收款人由单笔探针实测，条数与金额都要对上；付款行条数 = 成功笔数 |
| 四账号并发、其中一人零余额 | 零余额那笔必须被拒，且不牵连其余三笔；四人各自按自己成功笔数扣款；拒单不得留下付款流水（行数与金额都要对），分成也只按成交笔数发 |
| 同一请求连发 3 次 | 账与响应自洽；成交多于 1 笔时显著打印「待确认」 |

第二到四条都是「同账号两笔」，默认错峰 0.2 秒（`STAGGER`）；两条只发一对的（test_002 /
test_004）被频控污染时会重放（`PAIR_TRIES`，默认 3 次）。完全同时发时第二笔会被频控挡在
请求层，等于没测；具体依据见下文「错峰参数 STAGGER」与「成对被污染就重放」。

第一到四条把「少扣」和「超扣」都当失败：余额只留单笔（或两笔）的量，多扣一次就变负，被区间断言挡住。
第三条一次并发 8 个请求但按账号拆开对账，所以「响应说一笔、实际扣两笔」不会因为余额不足被掩成拒绝——真扣了就能看见。
它也是六条里唯一能覆盖「钱扣对了、分成却多发」的场景：同账号连发两笔，test_004 撞到的那次缺陷
就是钱只扣一笔、分成却发了两份。多写一行分成在余额上完全不体现，所以这条的收款侧也按流水对账。

第五条换到**收款侧**，但对账对象是**账户流水**（`xs_pay_change`），不是余额。
扣款在支付服务里扣，分成在结算服务里「按厅取比例 + 累加」，是两条链路：
后者错了要等主播对账才发现。而余额是下游结果，里面混着自己付款、渠道差异
（`money_cash` / `money_cash_b`）、到账迟到——用余额对账，少掉的那一笔很容易
被另一笔、另一个渠道、或收款人自己花掉的钱抵消掉，前几轮修的其实都是这些量法。

流水才是结算服务真正写下的东西：一行一个收款人，`reason` 里带 `from` / `gid` / `num` / `rate`，
`id` 自增可以当批次水位线（`id > 水位线` 就是这批的行）。「少写一笔分成」在这里就是少一行，抵消不掉。

**付款行按付款方 uid 认，不按 `op` 名认**：实测这个厅付款写的是 `op='consume'`，`op='pay'`
一次都没出现过。按名字认有两个后果：付款行被当成一条「收款写路径」（探针 1 个付款账号、并发 4 个，
键集合永远不相等，报出来的红是假的），以及「付款行数 = 成功笔数」这道校验因为探针付款行为空
整段跳过（两个都实际踩过）。`op='pay'` 仍算付款行，两种判据取并集。

所以口径全部由探针实测、不预设谁分成：先记水位线、发一笔、查出「这一笔到底写了哪些行」
（收款人是谁、`op` 是什么、各多少钱），并发再要求这些行**条数与金额都按成功笔数放大**；
付款侧还要求**每行都落在成交的那个账号名下**，且行数 = 成功笔数。厅配置从 71:6:3 变成
80:0:0 也不会红——配置变了就是探针值变了，只有「少写 / 多写一行」才红。

等待也按同一口径：**期望行数 = 探针实测行数 × 成功笔数**，直接当「等流水写到哪」的下界。
该写的一到位就返回，不必拿「静默一会儿」去赌；真漏写时行数永远到不了，一直等到超时，
再由断言判红。这条是上一次真机红的直接产物（见下文），旧的「行数静默 0.6 秒就收工」
在第 7 行 / 共 8 行时提前返回了。

余额只留一条粗校验，且只对主播（他不是付款方）：流水记了多少，钱包就得涨多少，
抓的是「账记了、钱没进钱包」这种两段式失败。

**「查不到流水」分两种，不能一律当未测到**：一种是结算压根没写库（成交了却没留痕，真缺陷），
另一种是流水写了但 `reason` 里不带 `gid`（我们的筛选口径失效）。探针阶段按 gid 查不到时会按
uid 兜底复查：两条口径都查不到 → 直接判失败；有行但不带 gid → 打印 `[未测到]` 并跳过，
并在输出里说明「本轮没有对账，别当成通过」。只有这一种跳过是允许的，`[未测到]` 也因此能在
`run_reproduce.py` 里被单独计数。

所有「未测到」都必须 `raise unittest.SkipTest`，**不能只打印、更不能 `return`**：`return` 在报告里
就是一条「通过」，cron 绿着而这条用例什么都没验到。这个坑踩过四次（同账号并发、自刷、重复提交、
同账号两笔全被频控挡下），现在由审计第 14 类静态拦住：哪个用例函数打了 `[未测到]` 却没抛
`SkipTest`，推送前的审计直接失败。

另外几种「流水看起来正常但钱是错的」也单独拦住了：

- **有付款行、一条收款行都没有**：早期版本会让「空 == 空」全绿过去，现在直接判失败（这笔钱没人收）；
- **被拒那笔留下付款流水**：零余额用例里成交几笔就该有几行付款流水，多一行就是「拒了单还扣钱」；
  金额同理：一行 100 记成 1，行数一模一样，钱却漏了，所以行数与金额两道都要对（期望值按探针实测放大）。
- **成交的那笔没有自己的扣款流水**：4 笔都 `success`、分成 4 行都写了，付款行却只有 3 行。
  2026-10-29 下午第一次真机跑这条用例就撞上了（`uid 200254777` 缺行）。只比总行数会把
  「A 少一行、B 多一行」互相抵消掉，所以付款侧要比**付款账号集合**，报错直接点名缺的是谁。
- **拒单也白送一份分成**：零余额那条里，被拒的账号若只回了响应、分成却照写，
  付款行数是 3、金额也对，**付款侧完全看不出来**。所以收款侧也对：分成只按成交笔数放大，
  多出一整倍就红。
- **自刷只成交一笔、分成却写了两份**：钱只扣一笔且扣得对、付款行也正常，只有收款行多一份。
  自刷分不出收付（付款方就是收款人），所以按（账号, op）分桶比，多出一个 `income` 桶就红。
- **下一轮的探针把上一条用例晚到的行当成自己的**：test_003 频控未测到直接 `SkipTest`，**没等自己那 8 笔落库**；紧接着 test_004 一取水位线，就把 `200250759` / `200252072` 的 consume 行算成了探针的写路径，期望值凭空多两条（`实际 2 条 / 期望 4 条`）——红的是自己的量法。两条修法：取水位线前先等流水表安静（`wait_flow_quiet`），自刷只看自己那个账号的行（`keep_uid`）。

要么结算漏写，要么我们读得太早。第一次现场只有聚合后的 key，分不开这两者，于是把
**原始行（id / uid / op / 金额）**也打进输出——id 的分布是唯一线索：同一批的 id 应该连着，
缺掉那一行如果稍后又出现，就是读得太早；完全不出现才是真没写。

第二次跑拿到的是后者：

#15395988 uid(200250759) consume 100元, #15395989 主播(200255399) income 80元,

为什么放弃余额对账（2026-10-29 实测，留档）：

| 轮 | 单笔（主播/厅长/公会长） | 并发增量 | 当时的口径 |
|---|---|---|---|
| 第一轮 | **71 / 未测 / 未测** | 284 = 4 × 71 | 厅配置 71:6:3 生效 |
| 第二轮 | **80 / 0 / 0** | 320 = 4 × 80 | 回落到默认 `as_normal` 0.8 |

71:6:3 三项相加正好也是 80，即**分成总池固定 80%，池内怎么分由配置决定**；默认口径下
80% 全归主播，所以第二轮厅长/公会长是 0。两次跑出不同单笔值，说明比例不能写死。

`money + money_b + money_cash + money_cash_b` 这个余额合计（查询名叫 `sum_money`，很容易
被当成「累计收入」，写错过一次）在两轮里各红过一次，都是我这边算错：

1. 把余额合计当成了累计收入，于是以为公会长打赏扣的钱不影响它——其实扣的就是他的
   余额，他那一刀 100 直接进了增量（`实际 -100, 预期 0`）。
2. 探针那一笔的到账落在「基线 → 并发」之间，被算进并发增量：主播 355 = 284 + 71。

**还没闭环**：厅 `170000211` 到底按 71:6:3 还是 80:0:0 分成、那 6%/3% 落在哪张表，
需要对照后台配置确认。流水版用例不依赖这个答案——探针查到几行就验几行，跑完看
`[并发-流水] 单笔探针：收款 ...` 这一行就知道本轮实际有几条写路径。
若探针那笔一条付款流水都没有（例如付款行不带 `gid`，框不出本批），付款侧无从对账，
用例打印 `[未测到]` 并 `SkipTest`——不再只是打印一句「只验了收款侧」就算通过。

**曾出现过一次（2026-10-29 上午）**：余额 100、并发两笔自刷，两笔都返回 `success=True`、
只扣 100（期望 200）——收一份钱、发两份货。之后用 `STAGGER` 0 / 0.1 / 0.2 / 0.3 / 0.5
各扫一轮，第二笔都稳定被**业务拒绝**（`success: False`、msg 为空），频控均 0 次，
五轮全未复现。所以它是窄窗口竞态，不是必现缺陷，也不能归因于限流。

再用 `run_reproduce.py` 跑 10 轮 + 30 轮（STAGGER=0）：**红 0 / 绿 37 / 未测到 3 / 无效 0**，
复现率 0%（0/37）——绿的都是 `下单前=100 现在=0 扣款=100 期望扣款=100 成功响应=1 笔`，
完全自洽。连上早先 STAGGER 扫描的 5 轮，**累计 45 轮、42 个有效轮次 0 次复现**。

> 按 rule of three，0/42 的 95% 置信上界约 **7%**：现在可以说「复现率低于 7%」，
> 但仍不能说「打不出来」——这条窄窗口确实存在，只是撞上的概率小。
> 另外 40 轮里有 3 轮命中频控变成「未测到」（约 7%），命中那一轮就白跑；
> 所以单看一两轮绿不能下结论，样本必须够。这也是 `run_reproduce.py` 要把
> 红/绿/未测到分开数的原因：混在一起，复现率会一会儿虚高一会儿虚低。

`test_004` 保留作为**回归钉**：它一旦再打出「成功 2 笔」，就是缺陷重现，直接提单；
平时应该保持绿，不要因为「曾经红过」就一直当红灯，也不要把断言调宽去凑绿。
已红过一次的现场就在提交历史里，真提单时拿它当复现材料，别等下一次红才动手。

自刷那条的**收款侧**单独一套判据：那次缺陷还有另一面——只成交一笔、分成却写了两份。
钱只扣了一笔、扣得也对，余额上完全看不出来，只有流水能抓住。但自刷时付款方就是收款人，
`split_flows` 按 uid 认付款行会把收款行一起算进去（收款侧一条不剩），所以改成按
**（账号, op）分桶**，不区分收付：整批的每个桶都必须是单笔探针的 `success` 倍，
被拒那笔若也分了成，就是凭空多出一整个 `income` 桶。等待下界同样是「探针行数 × 成功笔数」。

自刷还有个专属的干扰：这一批里只有它在下单，别的账号的行只可能是别的批次晚到的，所以读取时
加 `keep_uid` 只看自己那个账号——第一次进模块跑就是被这个绊了一下（上一条用例 `SkipTest` 时
没等流水落库，探针把别人的两行 consume 算成了自己的写路径）。

同一请求连发 3 次那条是**现状探测**：打赏请求体里没有幂等键（只有 `sign` + 业务字段），「重复提交几次算正常」属产品口径，口径确定前只记录不判红。跑完在输出里搜 `[重复提交][待确认]`，拿到实测结论后再固化成断言。

**手边已经有一份硬证据**（2026-10-29 默认错峰 0.2 的整跑）：4 个账号各自的两笔业务字段完全相同的请求全部返回成功、频控 0 次，每个账号各扣 200，分成 8 行 640 元、付款 8 行 800 元（#15396176~91），账与货自洽——说明这一版服务端**没有按业务字段去重**，连点两下会付两次。同一天另外两轮整跑是第二、第三个样本：分别有 3 个和 2 个账号的两笔都成交（各扣两笔钱），剩下那些账号的第二笔是被频控挡在请求层、与业务去重无关——三轮里一次都没见过「第二笔被服务端按业务字段拒掉」。注意限于此：`sign` 可能带时间戳，两笔并非字节级相同的报文，所以这只能证明「同一账号连提交两次就扣两次」，不能直接等同于「重放同一份报文」。是否要去重、按什么维度去重（账号 + 业务字段？订单号？），等产品口径。

#### 错峰参数 STAGGER（默认 0.2 秒）

服务端对**同一账号**限流：两笔完全同时发，必有一笔被「请求太快」挡掉，根本走不到
余额校验——用例虽然绿，却什么都没测到（输出会打 `[未测到]`）。所以「同账号两笔」的
三条（test_002 / test_003 / test_004）默认错开 0.2 秒。这个默认值是量出来的，不是拍的
（2026-10-29，同一版代码两轮对比）：

| STAGGER | 频控 | 结果 |
|---|---|---|
| 0（完全同时） | 4 次，4 个账号的第二笔全被挡 | test_003 只能转成「未测到」 |
| 0.2（现在的默认） | 只剩 1 次 | 3 个账号的两笔都真的走到校验：各扣 200、分成 7 行 560 元、付款 7 行 700 元 |

要复现「完全同时」的老口径就传 `STAGGER=0`，行为一模一样。要扫别的值：

```bash
for s in 0 0.1 0.2 0.3 0.5; do
  echo "=== STAGGER=$s"
  STAGGER=$s CASE=test_pay_concurrent.TestConcurrentPay.test_004 python3 run_stress_case.py slp \
    2>&1 | grep -E '并发-自刷|本轮命中频控'
done
```

`STAGGER` 只对「同账号两笔」的三条生效：test_002 / test_003 / test_004；test_001 / 005 / 006
是不同账号各一笔，不传错峰。test_003 早先漏传过——`STAGGER=0.2` 传了也不起作用，
跑出来和没传错峰那轮一模一样（2026-10-29 真机：4 次频控、每个账号的第二笔全被挡下）。

只看两个结果：**成功 2 笔**（缺陷复现，可提单）或 **成功 1 + 业务拒绝 1**（余额校验
真生效，绿得可信）。两种都不是（比如 `成功 1 + 频控 1`）不再靠反复调错峰量去找——
交给下面的成对重放，重放满 `PAIR_TRIES` 仍被挡才 `SkipTest`。某个账号仍被频控挡下的，
用例会点名打印「这一对没验到」，其余账号照常对账。

#### 跨用例的限流窗口（`SETTLE`，默认 1 秒）

错峰只解决「同一条用例里两笔挨太近」，解决不了「上一条用例刚打过同一个账号」。
2026-10-29 整跑就是这一种：test_001 一次 4 连发（不同账号、不传错峰）之后紧接着 test_002
又打 `200254777`，服务端的「请求太快了」落在 test_002 的第一笔上，整对变成
**成功 1 + 频控 1** → 只能跳过。当时还看到同一轮的 test_003（8 笔、同样错峰 0.2 秒）
一次频控都没有，于是以为根因是「被上一条用例打空了窗口」——后面两轮把这个说法推翻了。

没有服务端日志，分不清是「按账号的滑动窗口」还是「App 级令牌桶被 4 连发打空」，
所以不去猜：这三条用例发第一笔之前，按**本进程最后一次对这些账号发请求的时刻**等够
`SETTLE` 秒（默认 1），并把等了多久打出来。

```
[并发] test_002：上一条用例刚打过同一账号，等 0.10s 再发（跨用例的限流窗口不算这一条的结论）
```

但这一条**实测并不管用**，得说清楚：2026-10-29 加了 `SETTLE` 之后整跑，test_001 的断言
轮询（`assert_equal_eventually` 读 4 个账号）本身已经花掉 0.9 秒，所以这里只等了 0.10 秒，
test_002 依旧「成功 1 + 频控 1」，只能跳过。

三天下来的频控分布才是真线索：

| 轮次 | test_002（2 个请求） | test_003（8 个请求） | 其余（各 2~4 个） |
|---|---|---|---|
| 默认 0.2 首跑 | 1 次 | 0 次 | 0 |
| 加 `SETTLE` | 1 次 | 1 次（`200255209`） | 0 |
| 加 `PAIR_TRIES` | 0 次 | 2 次（`200255209`、`200252072`） | 0 |

**唯一稳定的规律是「一次 8 发那条每轮都中，2~4 个请求的都不中」**——从没见哪个 4 连发
的用例被挡过。这更像「整批请求量把令牌桶打空」，不像「按账号的滑动窗口」；但要确认
只能看频控落在时间线的哪一段，所以加了下面那条时序日志。

调大 `SETTLE` 仍被挡，就该去要服务端日志（限流规则才是根因），而不是把断言放松——
被挡下的是请求，不是「钱扣错了」，两者不能混为一谈。

#### 频控落在时间线哪一段（`[并发-时序]`，只在命中频控时打）

命中频控时输出里会多一行：每个请求**实际发出的时刻**（在错峰之后取，不是进线程的时刻）
和它的分类，按时间排开。

```
[并发] 本轮命中频控 2 次，错峰 0.2s，频控响应已原样计入业务拒绝（未重试），并发度保持完整
[并发-时序] +0.00s #0 uid=200254777 success，+0.21s #1 uid=200254777 success，……，
            +1.01s #5 uid=200255209 limited，+1.21s #6 uid=200252072 success，+1.41s #7 uid=200252072 limited
```

（上面是形状示意，时刻与序号以实际输出为准。）两种限流的落点不同，这一行就是分水岭：

- **按账号的滑动窗口**：挡的永远是「某账号的第二笔」，哪怕它排在最前面（`#1` 就中）；
- **App 级令牌桶被打空**：只挡时间上靠后的请求（前几个都过，从某处开始连续被挡）。

客户端拿不到服务端日志，这一行是唯一能把两者分开的证据。**所以它只打印、不断言**——
把猜测写成断言，等于在限流规则确认之前自己造红灯。反过来，记漏一条、或者把上一轮的
条目留下来，都会把一次频控指到错的账号上，比没有日志更糟，所以自检第 28 项钉住
「每条都记、每轮清空、异常那一路也要记」。

#### 成对被污染就重放（`PAIR_TRIES`，默认 3）

既然规则不清楚，这两条只用一对请求的用例（test_002 同账号两笔、test_004 自刷两笔）
改成：**拿到一对真的走到校验的请求才下结论**，被频控污染就冷却一下重放，最多三次。

```
[并发] test_002：上一轮被频控污染，等 1.0s 重放第 2/3 次
[并发-同账号] 成功 1 笔，频控 0 笔，业务拒绝 1 笔，响应 [...]（第 2 次尝试）
```

这**不是**放宽断言：每一轮都照原样重置余额、照原样对账，被挡下的那一轮只是不算数，
而且每次都打印（包括响应体）。频控发生在余额校验**之前**，那一轮根本没走到这条用例
要验的地方，拿它当结论才是错的。重放三次仍被挡，照旧 `SkipTest`——那时它就是一个
明确的「本轮没验到」，而不是一条绿。

两个细节容易写错，都是自检第 27 项钉住的：重放时重新拼一次报文（拿上一轮的 `sign`
重发可能因过期被拒，把频控换成了另一种假的未测到）；`flows=True` 时水位线要**每次
尝试前重取**，否则被污染那一轮写的流水会被算进这一轮。

test_003（一次 8 个请求）不重放：整批重放代价太大，它改成要求**至少两个账号**的这一对
真的走到校验，只剩一对时 `SkipTest`——拿一对去下「四账号各连发两笔」的结论太薄。

#### 拒绝响应不带原因（2026-10-29，待产品确认）

余额不足、零余额这两条拒绝路径返回的都是 `{'success': False, 'msg': ''}`——`msg` 是空串，
响应里也没有别的说明字段；同账号连发被余额挡下的那一笔同样如此。只有频控分支给了文案
（「请求太快了，请稍后重试」）。

对判定的影响已经兑掉了：`classify` 不靠 `msg` 分「业务拒绝 / 频控」，而 test_002 的
「被拒」另有 test_003 做交叉验证（余额够时两笔都成交），所以这一条**不阻塞用例结论**。

但它是个真实的体验问题：用户点打赏失败时，前端只能拿到 `success=false` + 空 `msg`，
没法告诉用户是「余额不足」还是别的原因。要不要补文案/错误码属产品口径，这里**不加断言**——
口径未定就加，只会得到一条没人认领的红灯；口径定了再把它钉成「余额不足必须带 msg」。

### 定时任务

服务器上每天 10:00 跑一轮全量，结果推到企业微信群。webhook key 放在**仓库外**的 `~/.slp_env`（权限 600），代码、crontab 里都不出现它。

**① 建凭据文件**（key 从企微群「群机器人」里取）：

```bash
cat > /home/<user>/.slp_env <<'EOF'
export WX_BOT_SLP='https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<key>'
EOF
chmod 600 /home/<user>/.slp_env
```

**② 装 cron**（可重复执行，会替换掉旧的同名任务）：

```bash
cat > /tmp/slp_cron <<'EOF'
# 每天 10:00 拉最新代码后跑全量并推送到企微；日志按日期落盘，同时清理 30 天前的
0 10 * * * . /home/<user>/.slp_env; cd /home/<user>/qa-slpPayTest && mkdir -p log && { find log -name 'cron_*.log' -mtime +30 -delete; git pull -q --ff-only; PUSH_WX=1 /usr/bin/python3 run_crontab_case.py slp; } >> log/cron_$(date +\%F).log 2>&1
# 每天 11:00 单独跑并发/幂等，与全量错开一小时
0 11 * * * . /home/<user>/.slp_env; cd /home/<user>/qa-slpPayTest && mkdir -p log && { git pull -q --ff-only; PUSH_WX=1 /usr/bin/python3 run_stress_case.py slp; } >> log/cron_stress_$(date +\%F).log 2>&1
EOF

(crontab -l 2>/dev/null | grep -v 'run_crontab_case.py slp' | grep -v 'run_stress_case.py slp'; cat /tmp/slp_cron) | crontab -
rm -f /tmp/slp_cron; crontab -l
```

两处过滤是为了可重复执行：`grep -v` 先把旧的两条都去掉，再写入新的，否则重装一次就会出现两条全量、两条并发同时跑。

第二条不带 `CASE=`：会跑 `caseStress/` 下全部文件（目前是并发打赏 + 重复提交），以后新增并发用例会自动纳入，不用改 cron。日志名以 `cron_` 开头，所以第一条里的 `find log -name 'cron_*.log' -mtime +30 -delete` 会一并清理，不另写一条。

为什么 key 单独放一个文件：crontab 内容是明文，能登这台机器的人 `crontab -l` 就看得见；而 webhook key 拿到就能往群里发任意消息。放 600 权限的文件里，至少跟登录权限一个级别，也不会随 crontab 内容被拷来拷去。

`. 文件;` 后面用**分号不用 `&&`**：凭据文件一旦不在了（换机器、误删），`&&` 会让整条命令短路——连用例都不跑，也不报错，看起来就像「今天一切正常」。用分号的话，用例照跑，只是不推送，日志里那行「未设置 WX_BOT_SLP」会说明原因。宁可少一条推送，不能少跑一轮用例。

推送形态：

| 本轮结果 | 群里的消息 |
|---|---|
| 全部通过 | 两行起：绿色 `通过 125 / 137` + 灰色尾注 `slp　跳过 12　重试 1　4m52s　lxm@3adcbba`；有跳过时再接一段灰色清单 `跳过 12 条（不算通过，本轮这几条没验）`，每条 `文件名 · 方法` + 一行原因 |
| 有失败/异常 | 橙色结论行 `2 失败　1 异常`（附灰色通过数）→ 灰色性质行 `环境 1　造数 1　断言 1`（全是断言时不列）→ 有未通过的场景族 → 编号清单：`1.`　`test_gs_room.py · test_007`、用例描述、一行原因（灰字）；非断言失败在标题后标 `(造数)` / `(异常·环境)`；最多列 10 条，其余指向 `log/notPassCase.log`。跳过清单排在失败清单之后 |
| 0 条用例 | 红色 `本轮 0 条用例被执行`，退出码 2——套件为空或 `CASE` 写错，不算通过 |
| 环境不可用 | 红色 `环境不可用，本轮未执行` + 探测失败的那几项，退出码 3——一条用例都不跑 |
| 执行中断 | 红色 `执行中断`：用例没跑完，退出码 2，堆栈落 `log/runCode.log` |
| 推送本身失败 | 只记日志不打退出码：网络抖动不该把「用例跑完了」说成「执行异常」 |

排版是给「扫一眼」用的：第一行只放结论，应用名/跳过/重试/耗时/版本全部下沉到最后一行灰字，没事的时候固定两行，变红的位置才会被注意到。失败清单靠缩进做层级、不用反引号（等宽字体夹中文很难读）。超过单条上限拆成多条时，第 2 条起标 `(2/3) 清单续`，避免续条在群里认不出属于哪一轮。

跳过不再只计数，理由要写出来。以前的前提是「跳过的都是已确认下线的功能」，只计数不列明细；现在「未测到」（单笔探针没成交、流水不带 `gid` 导致筛选失效）也走 `SkipTest`，那条用例本轮**一条断言都没验**。只给一个数字的话，群里看到的是一条绿色的 `通过 125 / 137`，没人知道其中有 12 条其实没测到。下线功能的 skip 理由写在装饰器里，清单里一眼就能和「未测到」分开。最多列 5 条，其余指向 `log/notPassCase.log`（那里是全量、带理由的 SKIP 清单）。

`run_crontab_case.py` 与 `run_all_case.py` 的区别：不拉取代码分支、不逐条播报通过用例，只出汇总和失败清单，适合无人值守。它也认 `CASE`（写法相同），改完汇总/落盘逻辑后不必跑完 137 条就能验证，加 `PUSH_WX=0` 就不会往群里发消息：

```bash
CASE=test_check python3 run_crontab_case.py slp
```

## 环境容灾

### 三层数据，只有一层需要备份

| 类别 | 例子 | 丢了会怎样 |
|---|---|---|
| **可自愈** | 余额、背包、等级、人气、加速卡、上周厅汇总 | 下一次跑用例时前置清理自己重建（`prepare_test_data` / `reset_room_acs` / `prepare_vip_pop_data` / `prepare_acceleration_card`），不需要人工干预 |
| **半可再生** | 点唱房记录、订单 | 造数能补，但得先清残留，否则断言会多出上一轮的金额 |
| **不可再生** | 账号、房间、工会关系、礼物/商品配置 | **造数也无从下手**（账号被删时连 `update` 都不知道往哪写），必须从快照恢复 |

所以备份只针对第三层。第一层备份了也是浪费：每次跑用例都会把它覆盖掉。

### 体检：把「环境被清」和「服务端改坏了」分开

这是比备份更紧急的一步。原来 `preflight` 只验连通性——数据库被清空也照样绿，然后一百多条用例集体变红，现象和服务端上线引入 bug 完全一样，排查方向从一开始就是错的。

现在多探一项「数据」，查的是种子表里那批账号/房间/礼物/工会还在不在：

```
[环境] OK    MySQL   <db-host>:3306 可读
[环境] OK    数据    账号/房间/礼物/工会 种子齐全
[环境] OK    Redis   <redis-host>:6379 可 ping
[环境] OK    接口    https://<api-host>/ 可达（HTTP 200）
```

缺了就点名到具体 id，并直接指路，退出码 3（与用例失败 1、没跑完 2 区分）：

```
[环境] FAIL  数据    账号缺 1 个：200250759；恢复 xs_user_index / xs_user_profile / xs_user_mobile 快照
[环境] 本轮不执行任何用例
[环境] 种子数据缺失通常是测试环境被清理或重置过。先用 python backup_seed.py list 看有无快照……
```

三点设计取舍：

- **点名不数数**：报「缺 uid=200250759」而不是「少 1 个」，前者能照着补，后者还得自己数
- **只查最小集**：误把一个不存在的资产写进清单，会让闸门每天误拦整轮回归，比不检查更糟
- **工会一项只警告不拦**：工会 id 与会长的 uid 同号，做成硬拦截容易误伤

### 快照：只导种子，几十 KB

```bash
python backup_seed.py dump --dry-run     # 先看会执行什么命令（本机没装 mysqldump 也能看）
python backup_seed.py dump               # 导出，默认保留最近 4 份
python backup_seed.py list               # 看已有快照
python backup_seed.py restore ~/.slp_backup/seed-2026-10-29-100000.sql --yes
```

- 存在仓库外 `~/.slp_backup`，权限 600：快照里有手机号，不能跟着代码进 git
- 密码走 `MYSQL_PWD` 环境变量，不进命令行——否则 `ps` 里能看到
- 小表整表导、大表按种子 id 过滤：不为省几 KB 去猜过滤列名，猜错就是把环境恢复坏
- 分两个文件（`xianshi` 与 `config` 库各一份）：mysqldump 的输出不带库前缀，混在一个文件里导不进去
- 恢复必须 `--yes` 或手动输入 `RESTORE`：这条命令会覆盖线上测试库

**只有环境好的时候导出来的快照才有用**，建议每周跑一次，别等到坏了才想起来导。

## 退出码

| 退出码 | 含义 |
|--------|------|
| `0` | 全部用例通过 |
| `1` | 存在失败或异常（跳过不计） |
| `2` | 没跑完：命令行参数错误（两个入口都只接受 slp / xsg，传错直接退出，不会静默跑一轮覆盖日志）、`CASE` 写错导致 0 条用例被执行，或执行中途抛异常（suite 构造异常、磁盘满等） |

在 `cmd && 下一步`、cron 告警、调度平台里都靠这个退出码判断本轮结果。

## 日志与报告

执行结束后控制台输出带编号的完整未通过清单（编号 / FAIL|ERROR|SKIP / 用例名 / des / 失败明细），随后一行「失败性质」把红点归堆（环境 / 造数 / 接口 / 断言 / 其他），同时落到 `log/`：

| 日志 | 内容 |
|------|------|
| `notPassCase.log` | 未通过清单，**排查先看这个** |
| `progress.log` | 逐条实时进度：`[ 37/137] FAIL  12.30s  test_xxx.test_004` |
| `failCase.log` | 失败与异常的完整堆栈 + **失败现场**（入参/响应/账户快照） |
| `retryCase.log` | **重试后才通过**的用例清单：哪一轮、哪个断言先失败 |
| `caseResult.log` | 每轮执行的条数汇总 + **失败性质**归堆 + 场景族统计 + 重试摘要 |
| `getSession.log` | token 获取情况 |
| `updateGitCode.log` / `gitBranchError.log` | 分支检查与上次执行时间 |
| `runCode.log` | 入口异常（如 App 名不认识）；重试摘要（只看这一个文件的人也能判断这轮有没有被重试兜住的问题） |

失败性质由失败文本自动判定（`common/report.py: failure_kind`），五类对应五种处理动作：

| 性质 | 典型文本 | 该做什么 |
|------|------|------|
| `环境` | `Can't connect to MySQL ... (timed out)`、`Max retries exceeded`、`Timeout connecting to server` | 先看环境，代码大概率没问题，修好后重跑 |
| `造数` | `pymysql` 的非连接类报错（表不存在、唯一键冲突） | 看用例前置的造数语句和脏数据 |
| `接口` | `Actual Code: 502, Expected Code: 200` | 服务端异常，找开发看网关/服务日志 |
| `断言` | `实际结果: 3600, 预期结果: 4200`（含轮询超时后缀） | 业务逻辑不符，查分成/结算口径 |
| `其他` | `KeyError`、`TypeError` | 脚本自身 bug |

```bash
tail -n 100 log/notPassCase.log   # 先看未通过清单
tail -f log/progress.log          # 跑到第几条、每条多久（另开一个窗口）
tail -n 200 log/failCase.log      # 需要堆栈与现场时再看
```

三个跟排查直接相关的设计：

- **进度写文件而不是只打控制台**：`python run_all_case.py slp | tail -60` 时 tail 要等 EOF 才输出，整个运行期间看不到任何东西，看着就像卡死；`log/progress.log` 可以边跑边看。每条附带本用例耗时（含重试），顺手能找出慢用例。
- **失败掉落现场**（`common/Scene.py`）：每条用例执行期间缓存最近 5 次请求/响应（入参 + HTTP 状态码 + 响应体），失败时连同打赏者/收礼人的 `xs_user_money`、`xs_user_profile` 快照一起写进 `failCase.log`。原来这些只在控制台滚一次，看不到了就只能重跑一轮。快照只观测不参与断言，自身异常全部吞掉，且只在失败时才读库。
- **重试可见**（`log/retryCase.log`）：`@Retry` 重试成功后用例状态是 PASS，和一次就过的用例长得一模一样。实测一轮全量有 **54 次重试**，也即 54 次真实断言失败被重试掩盖住了，而它们此前唯一的痕迹是控制台里滚过的那行 `[Retry 1/1]`。现在按用例归档成清单（含第几轮、失败明细），`progress.log` 的行尾也会标 `[重试×N]`。**看到「通过」时先问一句：是不是重试才过的**。

## 框架自检

```bash
python -m common.selfcheck      # 不连服务端、不连库，全部通过才退出 0，末尾会打印项数
```

覆盖六大类：频控退避、失败现场、异步读值轮询、环境种子清单、本机环境配置、并发用例工具，另有报告推送与 `CASE` 名字解析两项。

频控退避、失败现场、异步读值轮询这几类守护逻辑，真实全量里可能一整轮都触发不到（例如 2026-10-27 那轮 137 条全绿，一次频控都没撞上、一次失败都没有），于是「写了」和「真的按预期工作」之间始终差一步，等到真需要它的时候才发现坏了。自检用假 `requests`/假时钟把这几条分支固定走一遍：频控命中后退避重试、重试耗尽把响应交回用例、四种实测文案都能识别、退避间隔递增、非 json 响应不误判、现场能拼出入参/响应/账号快照且自身异常不影响用例结论，以及轮询版真的会重读、超时会写明等了多久、首轮命中只读一次。

并发工具那十一项是给流水对账用的：付款行按付款方 uid 认、不靠 `op` 名（实测付款写的是 `consume`），
条数稳定前会不会提前返回（`await_uids`：每笔都落了自己的付款行才算写完，光看行数会被
「A 少一行」骗过），分成按成功笔数放大会不会比得出来（整体比较：键集合、条数、金额一次比完；
只比总行数时「主播多一行、厅长少一行」会互相抵消，只比金额时「一条写路径掰成两条」看不出来），
同账号重复提交是否真有一对送到了校验（两笔全被频控挡下时扣款侧依旧「各扣一笔、全对」，
报告上却是通过），自刷按（账号, op）分桶后分成多发一份比不比得出来（付款方就是收款人，
按 uid 分收付会把收款行吞进付款行），取水位线前会不会先等流水安静、自刷会不会把别的账号
晚到的行滤掉（`wait_flow_quiet` / `keep_uid`：上一条用例 `SkipTest` 时不会等自己那批落库），
同账号两笔的默认错峰没被退回 0（退回后三条用例会整对被频控挡下、只能 SkipTest，报表上
只当又跑了一轮），跨用例的限流窗口会不会等（`SETTLE`：上一条用例刚打过同一账号时
等够秒数，早就过去了一口也不等，否则整个冷却就是个永不生效的空函数——
2026-10-29 整跑就是这么让 test_002 变成「成功 1 + 频控 1」的），成对被频控污染会不会
重放（干净的第一轮不重放、污染了要重放、到上限就交回去跳过、`flows=True` 时水位线必须
取最后一轮的，否则被污染那轮的流水会混进这一轮），频控时序日志会不会记全（每条请求的
发出时刻与分类、每轮清空、请求层抛错那一路也照样记一条，否则频控的位置会整体错位），
响应四分类（尤其网关返回 HTML 时 body 是字符串）会不会崩。
它们不是照代码抄一遍——把实现换回
有 bug 的版本，自检必须红，这一点每次改这十一项都要用探针验一次；否则自检就只是一段永远绿的代码，
比没有更糟。

`CASE` 那项盯的是「同一个用例名在两个入口两套写法」：带不带目录前缀都要装出同一批用例、不产 `_FailedTest`、前缀与实际跑的目录不一致或名字真写错时要当场退出并说清原因。它比用例本身更值得自检——现场踩过一次，`CASE=caseStress.…` 跑出来是一条 `No module named 'caseStress.caseStress'` 的假失败，看着像用例挂了。

另外一项容易被忽略的：**自检自身不能因为一项崩掉就中断整轮**。检查函数抛的不是 `AssertionError`（比如 `AttributeError`、连库超时），甚至被检查的代码自己 `sys.exit`（`build_suite` 拒绝加载写错的用例名就是这样），也要记成一条失败继续往下跑，否则后面那些项看上去就像「没报错」。

只验证框架行为，不碰任何业务预期值——改框架代码后跑一次，别等到线上红一轮才发现。

## 编写用例

约定（unittest 本身就要求这些）：

- 测试文件 `test_*.py`，测试类 `Test*`（不能写 `__init__`），测试方法 `test_*`
- 用例挂在 `caseSlp/` 或 `caseXsg/` 下，公共能力只写 `common/`；两侧 `tools.py` 只做转发，避免同一实现维护两份
- 用例方法第一个参数写 `des='场景,预期'`：报告按方法签名里的 `des` 默认值展示（取不到时退回 docstring），写得具体才能一眼看出挂了什么
- 断言一律带 `reason(des, res)`，失败时报告里能直接看到请求与响应
- 用例末尾的 `case_list_b[des] = result` 是历史写法（报告已改为从 unittest 结果里收集，不再读这几个 dict），新增用例可以只写断言

```python
@Retry(max_n=2, sleep=5)   # 只重试 AssertionError；skip 不重试
class TestPayCreate(unittest.TestCase):
    def test_001(self, des='点唱房-点歌,一首歌'):
        rid = gs_music_rid
        assert_equal(mysql.checkRidFactoryType(rid), 'business-music')  # 先确认环境数据
        prepare_test_data(payUid, uid, money=default_money, god_status={uid: 2})
        data = encodeData(rid=rid, payType='choose_song', money=money, order_songs=[...])
        res = post_request_session(pay_url, data, tokenName='slp', pay_uid=payUid)
        assert_code(res['code'])
        assert_body(res['body'], 'success', 1, reason(des, res))
        assert_equal_eventually(lambda: mysql.selectUserInfoSql('sum_money', payUid), default_money - money)
```

断言怎么选：

| 断言 | 用途 |
|------|------|
| `assert_code(res['code'])` | HTTP 状态码，默认期望 200 |
| `assert_body(body, 'success' 或 'msg', 预期, reason(des, res))` | 响应字段，多值可传元组当白名单 |
| `assert_equal(actual, expect)` | 等值；数值自动容忍 `1e-4` 误差（覆盖 `Decimal` 与 float 混比） |
| `assert_between(actual, low, high)` | 浮动区间，如分成比例 |
| `assert_equal_eventually(lambda: mysql.xxx, expect)` | **读账户表一律用它**：轮询读值，直到等于预期或超时 |

`assert_equal_eventually` 内部处理了三件容易踩的事：中间轮次的失败原因不会污染报告；超时后拿最后一轮的失败信息报错；失败原因里会注明「已轮询 N 次、等待 X 秒仍未达标」——「结算变慢」和「分账算错」看这一句就能分开。

**为什么读账户表必须走轮询版**：服务端扣款是同步的，收礼方分成却是异步落库。发完请求立刻同步读一次，收礼方那边必然还是 0。2026-10-27 那轮全量的实测：`137` 条用例里 **50 条（36%）是重试一轮才过的**，`log/retryCase.log` 里的失败明细几乎全是同一句 `实际结果: 0, 预期结果: 60/80/420/4620/...`。也就是说报告写着「通过 125」，其中几十条第一轮其实什么都没验到，全靠 `@Retry` 重跑一遍撞对了。现在全仓 567 处余额/统计断言统一改成轮询版：首轮就命中时只读一次（不打赏方扣款那种同步读值拖慢），要等时按 `WAIT_INTERVAL` 最多等 `WAIT_TIMEOUT`。

这条规则由 `pre_push_audit.py` 的第 6 项守着：`assert_equal(mysql.selectUserInfoSql(...))` 会直接审查不通过；把读值提前求好再传给轮询版（`assert_equal_eventually(mysql.xxx(...), expect)`）同样拦——那等于每次白等一轮超时。

重试是怎么跑的（`Retry` + `common/Request.py` 的回放）：

- 只重试 `AssertionError`；`SkipTest`、`TypeError`、`KeyError`、`DbQueryError` 不重试，重跑也不会变好
- 重试轮**不会重复下单**：首轮下单成功后，同参数的 `pay/create` 请求直接复用首轮响应，只重新做读库断言
- 首轮下单**业务失败**时不复用（`success != 1` 的响应不进缓存），重试会真的重发请求 —— 否则偶发失败会被回放固定成“连撞四轮同一个错”
- 数据准备类操作（改金额、插背包礼物）在重试轮跳过，避免把首轮已生效的造数覆盖掉

## 排查手册

1. **先单跑，再全量**。全量里随机 1~2 条红、单跑却必绿，基本是环境/缓存/顺序依赖，不是用例逻辑问题。
2. **注意时区差**。测试机是 CST（东八区），**MySQL 是 UTC**：`from_unixtime` 出来的时间会比机器时间差 8 小时。往时间窗口里造数据时不要卡边界（比如插「上周一 00:00」），要放在窗口中间，否则任何时区偏差都会让它掉出区间。
3. **Redis 连接配置的 key 是 `host_slp`**，不是 `host`；`conRedis.get(key)` 走的是 `decode_responses=True` 的连接，读 protobuf 之类的二进制值会抛 `UnicodeDecodeError`，这种场景用 `conRedis.getRawConn()`。
4. **看到「房间类型错误」先看失败现场，不用再复现**。这句文案也不再是孤证：`caseSlp/test_naming_song.py` 的下单一律走 `post_pay()`，命中房间类错误时会把现场写进失败原因（毫秒时刻 + `Room.Data` 的 `exists/ttl/len/has_factory_type` + `tavern_enable`/`gate_chseq` 两个开关 + 库内行数/类型/`deleted`/房主 + **本次请求耗时和后端实例标识**），据此一次就能分开几种情形：**行数≠1 或 `deleted`≠0 → 环境数据坏了**；**库内正确且两个开关与常态一致 → 服务端侧问题**；其中再看两条不需要服务端配合的线索——**耗时明显偏长（几秒 vs 百毫秒）→ 超时/慢查询**，**后端实例集中在同一个 IP → 某台实例异常/版本旧**（8% 这个量级很接近 1/12，一台/十二台）。

   后者实测**是服务端 bug，不是环境噪声**：13 轮命名颂（每轮 10 条）共失败 9 次，约 7%。三条排除性证据：

   - **耗时 27~42ms 就返回**：正常请求也是这个量级，所以不是超时/慢查询——服务端在本地判断里直接拒了，没走到慢 RPC
   - **同一时刻库内配置正常**：`xs_chatroom` 44 个字段里 `type=listensong`、`types=joy`、`room_factory_type=business-music`，与成功请求完全一致
   - **相关缓存全部正常**：`Room.Data`（binlog 刷新后 DEL、请求时回源重建，miss 属正常）、`Room.Desc`（只是房间名）、`slp.tavern.room.enable`（`xs_chatroom` 里根本没有 tavern 字段，它是另一条业务线的开关，`'0'` 对点唱房而言是正确的）、`room.gate.chseq`（常态也是 None）、代码删房间（零调用）

   同一个房间、同一份配置，92% 的请求放行、8% 报「房间类型错误」——这是服务端侧的问题。

   注意口径：同一个失败，单跑命名颂时报告显示 `重试后才通过: 1 条（10.0%）`（分母 10 条），跑全量时显示 `0.7%`（分母 137 条，而这个文件只跑一轮）。**别被全量里的 0.7% 麻痹**——对点歌/冠歌这条链路，每轮 10 条里就有一条会被服务端拒掉，真实失败率 10%。要盯这个 bug 就单跑这个文件，信噪比高得多，看趋势也快。

   **不要用「清缓存」「放宽重试」去消掉它**。那样做能让报告变绿，但 bug 就此查无实据。客户端只负责适配环境、保证用例正确执行；`@Retry(max_n=3, sleep=5)` 兜底只代表这条用例不会红，不代表问题不存在——所以每轮输出固定打印一行 `重试后才通过: N 条（X%）`，这个百分比就是它的存在证明，服务端修好后会掉到 0，恶化会涨。

   （排查记录里的一个坑：前 7 轮恰好每轮 1 条，据此算过「连续 7 轮恰好 1 条的概率只有 0.09%，所以是周期任务」。这是**事后偏差**——「恰好 1 条」是观察完才挑出来的特征；再跑 3 轮就有 2 轮一次没失败，周期性假设直接作废。判断是不是随机，不能只挑一个事后的统计量来算概率。）

   另外没必要主动删 `Room.Data.<rid>`：库数据正确时，缓存刷新交给 binlog 同步任务即可——实测缓存绝大多数时间不存在（`ttl=-2`），但用例照样通过，「缓存不在」本身不是判据。

   （历史坑：重试轮曾复用首轮的业务失败响应，四轮都不重发请求，看起来像服务端持续故障；已由 `common/Request.py` 的 `_is_business_success` 修掉，改回放逻辑时别退回去。）
5. **环境数据先行断言**。用例开头用 `checkRidFactoryType(rid)` / `checkUserBroker(uid)` 这类断言确认房间类型、公会关系，环境被改坏时能一眼看出是“数据不对”而不是“代码坏了”。
6. **改完先编译**：`python3 -m compileall -q caseSlp caseXsg common`，比跑一遍全量快得多。

## 这个仓库的第一原则

**这些 case 是为了发现服务端支付接口的逻辑问题而存在的，不是为了交一份全绿的报告。**

由此推出两条硬约束：

1. **验证逻辑必须严谨正确**。断言口径只能是「服务端应该做什么」，不能因为跑不通就往回调。
2. **允许增强健壮性，不允许弱化校验**。测试环境复杂、有异步落库、有频控、有慢查询，这些可以靠脚本适配；但适配的对象永远是**环境噪声**，不是**断言标准**。

| 合法适配（环境噪声） | 禁止（弱化校验） |
|---|---|
| 异步落库→ `assert_equal_eventually` 轮询等到达 | 把精确值改成「非空/存在即可」 |
| 频控 → `REQUEST_INTERVAL` 退避重发 | 把断言注释掉 |
| 网络抖动 → `@Retry` 真重发（失败响应不缓存） | 用 `skip` 躲开已知失败 |
| 慢环境 → 调大超时上限、拉长轮询窗口 | 把断言包在 `if` 里，条件不成立就静默跳过 |
| 造数、清场、准备缓存 | 用 `try/except: pass` 吞掉断言失败 |

两者的区别只问一句：**这个改动是让「真实结果」更稳定地读出来，还是让「不真实的结论」显得更好看？** 前者做，后者一律不做。

由 `pre_push_audit.py` 第 7 项守者：条件断言、被 except 吞掉的断言、被注释掉的断言、大于 1 的数值容差都会直接审查不通过；skip 数量偏离基线（装饰器 8 / 运行时 3）会给出提醒。

## 提交约定

- **分支：改动都提交在 `lxm`，服务器定时任务也跟 `lxm`**

  ```bash
  git push origin lxm
  ```

  服务器工作副本就停在 `lxm` 上，cron 里的 `git pull` 拉的是当前分支的上游，不需要写分支名。

  `master` 保留一份 fast-forward 快照（直接 clone 时默认分支就是最新的），两条分支永远指向同一个提交：

  ```bash
  git checkout master
  git merge --ff-only lxm
  git push origin master
  git checkout lxm
  ```

  `--ff-only` 不是可选项：它拒掉任何合并提交，两条分支永远是同一条历史线。否则一旦 master 上多出一个 merge commit，同步就变成「两边各自长东西」，以后想合只能手工挑提交

  只推 `lxm` 不影响定时任务，master 忘了同步也只是快照旧一点——把服务器指向开发分支，就是为了避免「代码推上去了但服务器还在另一个分支上等」这种静默偏差

- 提交信息用中文写清「为什么改」，一次提交一件事
- 用 `git add -u`（只暂存已跟踪文件）而不是 `git add -A`，别把临时脚本、日志、`.commit_msg.txt` 带进提交
- 推送前跑一遍 `python pre_push_audit.py`（十四类检查）：解析与 import、重构函数的分支覆盖、悬空调用、未用 import、零引用定义、账户读值写法、**验证强度**、**密钥泄露**、**场景族登记**、**未定义名字**、**调用点实参与签名**、**format 占位符与实参**、**内网地址与环境标识**、**「未测到」必须中止**。退出码非 0 就不要推
